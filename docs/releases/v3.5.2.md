# ぷるもぐサーチ3.5.2 / 地図更新時の停止を削減

地図を受信したときに画面が一瞬止まる処理を改めました。Windows版ZIP全体を展開し、`PurumoguSearch.exe`を起動してください。通常のウィンドウ、サイズ変更、最大化に対応しています。

## 改善内容

- 地図の格子生成をワーカースレッドへ移動。描画側では完成した頂点・色・インデックスをメッシュへ反映します。観測履歴は順序を保ち、観測／推定の区別、人・ガス・浸水の色も維持します。
- 推論評価も別スレッドで計算。物理空間の正解照合だけを同じ物理時点で取得し、評価計算はそのコピーを使います。正解が推論へ流れる経路は追加していません。最終保存は評価の完了を待ちます。
- 機体の球・円錐の表示を直前の2つの物理姿勢の間で補間。未来へ外挿せず、衝突・センサー・接続点を動かしません。
- 毎フレームの全ノード部品検索を廃止し、選択が変わったときだけ描画レイヤーを更新。GUIスタイルを再利用し、ノード表を10Hzで更新して画面外の行を描きません。
- 物理計算のまとめ実行に約4msの時間枠を設け、処理が遅れたときもカメラ操作へ制御を戻します。物理刻み20ms、観測25ステップ、地図要求間隔、推論モデルと入力条件は維持します。

## 検証方法

同じPC、48台、E06/L字エリア、地形・人物シード20261027で、改善前と改善後をそれぞれ50秒動かしました。起動後5秒を除き、地図生成・評価・描画反映のメインスレッド処理時間を記録します。24台と36台では層状の部分崩落C04も確認します。

測定は非表示ウィンドウでのCPU処理時間です。隠れたウィンドウではUnityが画面への表示を省略するため、ログのループ回数からモニター上のFPSを計算していません。GPU性能・最大化時の解像度・他アプリの負荷によって表示速度は変わります。

| メインスレッドの実測 | 3.5.1 | 3.5.2 |
| --- | ---: | ---: |
| 地図更新1回の平均 | 108.36 ms | 0.66 ms（投入0.02＋反映0.65） |
| 評価更新1回の平均 | 25.71 ms | 1.29 ms（正解取得・コピー・投入） |
| カメラ更新1回の平均 | 0.051 ms | 0.0034 ms |
| 50msを超えたCPUループ間隔 | 10回 | 0回 |

地図の別スレッド処理時間を0.66msへ短縮したという意味ではなく、描画を止める側の処理を移した結果です。測定PCはCore Ultra 7 265K／RTX 5080です。[元ログと比較表](../../reports/rescue/render-v352/)に条件を記録しています。

検査は、同期版と非同期版の全メッシュバッファ・危険色・評価値の一致、評価用の位置スナップショット、リセット後の古い結果の破棄、補間前後の剛体・衝突形状・接続点の不変性を含みます。`scripts/Unity-Task.ps1 -Task rescue-render-smoke`で再実行できます。

## 利点と制限

地図を更新しながらカメラ操作へ処理を戻せるようになり、機体の見た目も物理刻みの間を滑らかにつなぎます。地図の解像度やノード数を減らす処理は入れていません。

計算量そのものがゼロになる改善ではなく、別スレッド用に地図と評価のメモリーを使います。機体表示には最大1物理ステップ（通常速度で約20ms）の遅れがあり、推論待ちが長い場合は実際の探索も待機します。観測していない動きで埋め合わせません。重い環境ではまず標準ウィンドウサイズで使うと描画負荷を抑えられます。

36シーンと同梱モデルは3.5と同じです。追加学習や95%の再認定は行っていません。[完成範囲と精度](https://github.com/Applekeynote/purumogu-search/blob/v0.3.5/docs/v35-completion.md)を参照してください。
